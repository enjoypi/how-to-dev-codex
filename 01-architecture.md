# 01 System Architecture and Design Rationale

Verified against: commit `430a16799d`. Paths are relative to `codex-rs/` unless otherwise noted.

## 1. Layer Overview

```
┌ Entry layer ────────────────────────────────────────────────────────┐
│ cli (entry) arg0 (argv[0] dispatch) tui (interactive) exec (headless)  │
│ app-server-daemon (daemon management)                                  │
├ Protocol layer ─────────────────────────────────────────────────────┤
│ app-server-client (in-process/remote) app-server (MessageProcessor)    │
│ app-server-transport (stdio/unix/ws) app-server-protocol (v2 JSON-RPC) │
│ protocol (Op/Event core types)                                         │
├ Core layer ─────────────────────────────────────────────────────────┤
│ core (ThreadManager/Session/turn loop) core-api                        │
│ thread-store (storage abstraction) rollout (JSONL) state (SQLite)      │
├ Capability layer ───────────────────────────────────────────────────┤
│ tools apply-patch shell-command exec-server codex-mcp rmcp-client      │
│ hooks skills plugin core-plugins sandboxing linux-sandbox execpolicy   │
├ Infrastructure layer ───────────────────────────────────────────────┤
│ model-provider codex-api codex-client http-client config login otel   │
│ features secrets keyring-store utils/*                                 │
└─────────────────────────────────────────────────────────────────────┘
```

The layering is conceptual, not enforced: lower-layer crates commonly depend on `codex-protocol`, and `core` and `thread-store` also depend on `codex-app-server-protocol`. CI enforces only one rule: `tui` must not depend directly on `core`, checked by `.github/scripts/verify_tui_core_boundary.py`.

## 2. Why Rust

| Reason | Evidence |

| The sandbox must call Linux system APIs such as seccomp and Landlock directly | Same as above |

## 3. Entry: Single Binary and arg0 Dispatch

**Mechanism**: `main` in `cli/src/main.rs` wraps all logic in `arg0_dispatch_or_else`. It first calls `arg0_dispatch` in `arg0/src/lib.rs`, which checks in order:

1. The executable name is `codex-linux-sandbox`: enter the Linux sandbox.
2. The file name is `apply_patch`/`applypatch`: enter the patch tool.
3. argv1 is an internal marker (Windows MXC sandbox, exec helper process, fs helper process, Windows sandbox wrapper, in-core apply_patch): enter the corresponding helper entry point.
4. None of the above: load `.env` and inject the alias directory into `PATH`.

Then `arg0_dispatch_or_else` spawns a `codex-main` thread, starts the Tokio runtime in it, and hands off to `cli_main`.

Subcommands: no subcommand, `resume`, or `fork` goes to `codex_tui::run_main`; `exec` goes to `codex_exec::run_main`; `app-server` goes to `codex_app_server::run_main_with_transport_options`.

**Why**:

- #1086 (`89ef4efdcf`) original text: "we still want to deploy the Rust version of Codex as a single, standalone binary rather than a CLI and a supporting sandboxing binary". The sandbox process re-executes itself via `current_exe`, so no extra files need to be distributed.
- Dispatch happens before Tokio starts, while the process has only one thread, so `execvp` and seccomp setup are safe.
- `apply_patch` is injected into `PATH` as an alias, so `apply_patch` commands generated by the model run directly without installing a separate tool.
- #1697 (`9102255854`) extracted this logic into a standalone `arg0` crate.

## 4. Between Frontends and Core: the app-server Protocol

**Mechanism**: Session and turn execution in both `tui` and `exec` go through `app-server-client` over JSON-RPC; `exec` still depends directly on `codex-core` to load config, initialize the state DB, and check execpolicy:

```
tui / exec ──► app-server-client ─┬─ InProcessAppServerClient (in-memory channel, default)
                                  └─ RemoteAppServerClient (ws / unix socket)
                                              │
                                              ▼
                              app-server::MessageProcessor
                                              │  turn_processor: request → Op
                                              ▼
                                   core::ThreadManager / CodexThread
                                              │  bespoke_event_handling: EventMsg → v2 notification
                                              ▼
                                       back to client
```

`exec/src/lib.rs` calls `InProcessAppServerClient::start`; `tui/src/lib.rs` can optionally use `RemoteAppServerClient::connect`.

**Why**:

| Reason | Evidence |
|---|---|
| app-server was originally built for the VS Code extension: "used to power experiences such as the VS Code extension" | `d9dbf48828` (#4471) |
| In-process mode keeps app-server semantics without a process boundary, avoiding a "second execution contract" | Module docs of `app-server/src/in_process.rs` |
| exec migrated first; TUI migrated in stages (a parallel `tui_app_server` was maintained for a time), then gained remote auth | `da3689f0ef` (#14005), `9dba7337f2` (#14512), `db89b73a9c` (#14717), `1ff39b6fa8` (#14853) |
| TUI had long depended directly on core with no way to stop it getting worse, so a boundary check was introduced; remaining calls were consolidated into `legacy_core` to be removed gradually | `66e13efd9c` (#17399) |

Result: CLI, IDE, desktop app, and SDK share one protocol and one test suite, and new frontends need not understand core internals. Desktop app and SDK as motivations are inferred: the root `README.md` describes the IDE and desktop app (`codex app`), and the only basis for the SDK is the `sdk/` directory.

## 5. Core Runtime: Session and Turn Lifecycle

**Structure**:

- `ThreadManager` in `core/src/thread_manager.rs` provides `start_thread`, `resume_*`, and `fork_*`, producing `CodexThread` (`core/src/codex_thread.rs`, exposing `submit` and `next_event`).
- Each thread has a pair of channels, a bounded submission channel and an unbounded event channel, created in `core/src/session/mod.rs`; `submission_loop` consumes submissions and is defined in `core/src/session/handlers.rs`.

**One turn**:

```
Op::TurnInput
   │ dispatched by session/handlers.rs
   ▼
tasks/regular.rs ──► session/turn.rs::run_turn
                        │ auto-compact context when needed
                        ▼
                  run_sampling_request (loop)
                        │ try_run_sampling_request
                        ▼
                  ModelClientSession.stream ──► ResponseEvent stream
                        │ OutputItemDone
                        ▼
                  stream_events_utils::handle_output_item_done
                        │ ToolRouter::build_tool_call detects tool calls
                        ▼
                  ToolCallRuntime::handle_tool_call (concurrent, added to in_flight)
                        │
                        ▼
                  drain_in_flight collects results, fed back as next-round input
                        │ needs_follow_up ?
             ┌──────────┴──────────┐
            yes: keep sampling   no: run Stop hooks, TurnComplete
```

**Model call chain**: `ModelClient` in `core` → `model-provider` (auth, Bedrock, workspace routing) → `codex-api` (`ResponsesClient` / `ResponsesWebsocketClient`) → `codex-client` (HTTP, retries, SSE). `responses-api-proxy` is a standalone reverse proxy (`codex responses-api-proxy`) for injecting the API key and is not in the default path.

**Why queues and events**: `docs/protocol_v1.md` (introduced with #629) states that Codex communicates through a submission queue and an event queue and can run in a background thread or a separate process, "intended to be operated by arbitrary UI implementations". An async event stream naturally fits streaming output, concurrent tool calls, interrupts, and waiting for approval. There is no direct evidence for the trade-off against direct function calls; this is inferred.

## 6. Protocol

| Layer | Content | Stability |
|---|---|---|
| `protocol` | `Op` (submissions, `non_exhaustive`), `Event`/`EventMsg` (events) | Internal protocol; no wire-format guarantee |
| `app-server-protocol` | JSON-RPC 2.0; methods are declared via macros in `src/protocol/common.rs`, e.g. `thread/start`, `turn/start`; server requests such as `item/commandExecution/requestApproval`; notifications such as `turn/completed` | Stable for external use, except methods marked `#[experimental(...)]` |

Hierarchy defined in `docs/protocol_v1.md`: Session → Task (at most one at a time) → multiple Turns; the output of one Turn is the input of the next.

**Why precompute schemas**: `acd540f158` (#36212) original text: "Normal app-server protocol builds do not need the `ts-rs` and `schemars` implementations". Regular builds use no-op derives (`app-server-protocol-noop-macros`), and at runtime `generate_ts` decompresses `schema/precomputed/*.json.zst` directly; the real generators are enabled only when regenerating fixtures and in tests, which shortens compile times. `e1e2257e29` (#54113) went further and generates and embeds them at compile time in Bazel.

## 7. Tool System

```
model emits function_call
   │
   ▼
           router.rs ──► registry.rs::dispatch_any_with_state
                           │ PreToolUse hooks
                           ▼
                         orchestrator.rs: approve → pick sandbox → run → escalate and retry if denied
                           │
         ┌─────────────────┼────────────────────┬──────────────┐
         ▼                 ▼                    ▼              ▼
   unified_exec      apply-patch          mcp_tool_call     skills/plugin
   → exec-server     (in-process or      → codex-mcp
   (local/remote)        arg0 self-exec)     → rmcp-client (stdio/HTTP/OAuth)
                           │
                           ▼
                         PostToolUse hooks ──► feed result back
```

`router.rs`, `registry.rs`, and `orchestrator.rs` all live in `core/src/tools/`.

| crate | Responsibility |
|---|---|
| `tools` | ToolSpec and base types for Responses tools |
| `shell-command` | Command parsing and safety checks |
| `exec-server` | JSON-RPC subprocess and filesystem service; can be deployed remotely |
| `hooks` | Events such as SessionStart, UserPromptSubmit, Pre/PostToolUse, and Stop |
| `skills` | Loads `SKILL.md` and handles mentions |
| `plugin` / `core-plugins` | Plugin package model; directory and enablement policy |

**Why split out `tools`**: `44d28f500f` (#15923) notes that schema parsing was already called by code outside core, and keeping it in core made crate boundaries hard to understand; `be5afc65d3` (#15928) then extracted the MCP schema adapter.

## 8. Persistence

| Layer | Form | Purpose |
|---|---|---|
| `thread-store` | `ThreadStore` trait with Local and InMemory implementations | Unified session storage and retrieval; core is backend-agnostic |
| `rollout` | `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-*.jsonl` | Append-only full session record for resume/fork/replay |
| `state` | SQLite | Metadata index and log database |

**Why**: `dae56994da` (#17659) introduced `ThreadStore` to mediate access to JSONL and SQLite in one place; the module docs of `thread-store/src/lib.rs` call it "Storage-neutral". `6e72f0dbfd` (#17826) once added a remote gRPC implementation, and `79ad209ce6` (#21596) moved it out of this repository.

## 10. Why Crate Features Are Banned

| Reason | Evidence |
|---|---|
| Features create feature combinations that exist only under Cargo; the team is eliminating them, and the allowlist only shrinks | `dc263f5926` (#16455) |
| A feature caused codex-core to be compiled twice | `b68a84ee8e` (#11393) |
| `--all-features` consumes a lot of disk space | `264fc444b6` (#12429) |
| The Bazel build does not support crate features | Error text in `verify_cargo_workspace_manifests.py`: "our Bazel build setup does not honor them today" |

Enforced by `.github/scripts/verify_cargo_workspace_manifests.py`. #17826 once put proto generation into an example target to work around this rule.

## 11. Why Cargo and Bazel Coexist

- `codex-rs/docs/bazel.md`: Bazel provides hermetic builds, toolchains, and cross-platform artifacts; Cargo remains the single source of truth for crates, and `MODULE.bazel` reads `Cargo.toml` and `Cargo.lock` via `crate.from_cargo`.
- `2a06d64bc9` (#8875): remote builds via BuildBuddy; macOS artifacts are cross-compiled on Linux and tested on the native host.
- `.github/workflows/README.md`: `bazel.yml` is the main PR path for fast feedback; for remote caching, see #10079 and #9616.
- Developers use Cargo day to day. Bazel is the main CI path at the PR stage; official releases are still built by Cargo, while Bazel release artifacts are produced in parallel for reference only (`continue-on-error` in `rust-release.yml`).
